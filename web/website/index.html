Why SELECT

Every language in your stack has real tooling. Except SQL.

In the editor you already like you get completion, go-to-definition, lint on save, a formatter and twenty years of git history. Then you open your SQL client and you get a text area, a Run button, and a tab called Script-14.sql that nobody will ever read again.

That is not a missing feature. It is the wrong shape. SQL is code. It gets reviewed, refactored, blamed, reverted and rewritten by whoever picks up the ticket next. It should live where the rest of your code lives, and be edited by something that understands it.

The mature clients are not badly built. They are built for someone else. They grew up serving the person who administers the database, and the developer writing SQL between two commits was never their customer.

We only build for that developer. Files instead of a workspace database. Git instead of a share button. A keyboard instead of a wizard. One grant instead of an admin ticket.

01 · The editor

Completion and lint that read your schema

Point it at PostgreSQL, MySQL or SQLite and it reads the whole schema. Completion gives you real tables, columns, types and keys, not a keyword list, and the graph view draws how they join.

Lint parses your query and checks it against that schema as you type: the column that does not exist, the id that is ambiguous across two joins, the CTE you stopped using, the = NULL that silently matches nothing.

Your own rules go in a file in the repo, scoped by path, so the rule your team agreed on is the rule everyone gets. ⌘↵ runs. Nothing here needs the mouse.

02 · The workspace

Review a query like you review code

The last place your team's SQL lived was a Slack thread.

A workspace is a folder of .sql files with names you chose. Branch it, diff it, open a pull request against it, on whatever git host you already use. Your teammate's fix arrives the way every other fix arrives, and git blame works on it.

Git is built in, and optional. A plain folder is still a workspace, and your secrets stay in .env either way.

03 · The team

Stop asking someone for prod

Access is usually all or nothing, which is why the answer is usually no. Grant a column instead of a database: four levels of data (database, schema, table, column) and five actions (SELECT, INSERT, UPDATE, DELETE, DDL).

Read orders on production without ever seeing customers.email, and without a DSN on your laptop. Every query through the server lands in an audit log, so "who ran that" has an answer. Narrow enough that someone can finally say yes.

Agents

Give your agent a key, not the keys

You already point Claude Code and Cursor at your repo. Point them at your database the same way. The MCP server exposes seven read and write tools and nothing else: no shell, no filesystem. An API key carries roles, and those roles are exactly what the model can touch, down to the column.

The chat panel in the app runs on the same bounds, with your own API key and your own choice of model.
